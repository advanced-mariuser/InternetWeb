## Документ по проектированию: Алгоритм обработки TC флага
### Что такое флаг усечения (TC)?
Протокол DNS исторически был разработан для работы поверх UDP, так как это быстрый протокол без необходимости установления соединения. Однако у UDP есть ограничение: максимальный размер датаграммы. Изначально он был ограничен 512 байтами. Если DNS-ответ (включая все записи: Answer, Authority, Additional) превышает этот лимит, сервер не может отправить его целиком по UDP.
   
В этом случае сервер формирует усеченный (truncated) ответ. Он включает столько записей, сколько помещается в 512 байт, и устанавливает в заголовке специальный флаг — TC (Truncation). Этот флаг является сигналом для клиента: "Ответ слишком большой, я отправил все, что смог. Пожалуйста, повтори свой запрос, но уже по TCP". 
### Алгоритм обработки TC флага
   Обработка флага TC требует от DNS-резолвера реализации "плана Б" — перехода с UDP на TCP для получения полного ответа от того же сервера. Наш резолвер реализует этот механизм следующим образом:
   1. **Основной путь (UDP):** Все DNS-запросы по умолчанию отправляются через UDP, как это предписано стандартом. Метод Resolver::PerformQuery создает UdpSocket, отправляет запрос и ожидает ответ в течение 5 секунд.
   2. **Обнаружение флага:** После получения UDP-ответа, создается временный объект DnsMessage для предварительного парсинга заголовка. Вызывается метод IsTruncated(), который проверяет состояние TC-бита в поле флагов.
   3. **Переход на TCP (Fallback):**
      - Если `IsTruncated()` возвращает true, резолвер понимает, что ответ неполный.
      - В консоль (в режиме отладки) выводится сообщение: "UDP response truncated. Retrying with TCP...".
      - Создается новый объект `TcpSocket`.
      - Выполняется `tcpSock.Connect()` к тому же IP-адресу DNS-сервера, который отправил усеченный ответ, на порт 53.
      - Формирование TCP-запроса: DNS поверх TCP имеет важное отличие: перед самим DNS-сообщением необходимо отправить 2 байта, указывающие его длину. Поэтому мы создаем новый буфер `tcpQuery`, куда сначала помещаем длину оригинального запроса (преобразованную в сетевой порядок байт с помощью htons), а затем — сам оригинальный запрос.
      - Запрос отправляется через `tcpSock.Write()`.
   4. **Чтение TCP-ответа:**
      - Сначала `tcpSock.Read()` читает первые 2 байта из TCP-потока, чтобы узнать длину входящего DNS-сообщения.
      - Затем он входит в цикл и читает из сокета ровно столько байт, сколько было указано в поле длины, гарантируя получение полного ответа.
   5. **Возврат результата:** Полный ответ, полученный по TCP, возвращается в основной цикл резолвера для дальнейшей обработки (поиска A/AAAA записей или NS-записей).
